1概述

本工程是一个智能家居中控屏的 UI 应用程序，基于 LVGL 9.4 和 lvframe v0.2 页面管理框架开发。

  • UI 渲染：基于 lvframe 的多页面管理，支持左右滑动切换设备页、下拉进入设置页等交互
  • 业务逻辑：通用数据模型管理（设备 + 虚拟模型），支持通过 Shell 命令行与 UI 双向联动
  • UI 与业务交互：LVGL 与业务逻辑运行在各自独立的线程中，通过 两个消息槽（g_ui_slot / g_dev_slot）解耦通信；消息按信号（signal）+ 对象（object）分发，object 为数据模型指针（NULL=广播），由槽在分发时匹配

线程与数据安全总则（详见线程架构与业务交互）：

  • UI 操作（点击开关等）构造消息 → 发送到 g_dev_slot → DEV 线程消费并修改数据模型 → Shell 输出日志
  • Shell 指令由 DEV 线程解析，修改模型后按信号经 g_ui_slot 通知 UI（object = 模型指针）
  • 添加/删除模型需严格管理生命周期：删除必须先销毁 UI 页面，再释放数据模型（DEL → UI 销毁 → DEL_ACK → DEV 释放）
  • UI 页面通过 page_bind_slot(page, slot, signal, object) 按信号 + 对象订阅，object 由槽匹配；数据读取走仓库快照接口；DEV 线程是数据模型唯一所有者

本文档依据 v2 设计编写（动态节点槽、signal + object 匹配、payload 由槽释放），方案未定，代码待审核通过后实施。与旧版（event_bus + app_bus）设计不同，详见lvframe 框架设计文档 v2。

4.4 设备页分发与绑定（device_page.c）

5数据模型（通用模型层）

6消息定义（信号化双槽）

消息枚举由应用定义（msg.h），框架不做任何限制；一个数据模型可细分多个信号（如灯：开灯 / 关灯）。槽按 signal + object 分发（object=NULL 双向通配），object（模型指针）由槽匹配。

typedef enum {
    /* → g_dev_slot（DEV 线程消费）*/
    MSG_UI_SET_PROP,     /* object=模型, field=属性名, arg0=新值 */
    MSG_UI_SET_SYSTEM,   /* object=SYSTEM 模型, field=字段, arg0=新值 */
    MSG_UI_DEL_ACK,      /* object=模型（UI 已销毁页面，可释放）*/

    /* → g_ui_slot（UI 线程消费）：设备信号 */
    MSG_DEV_LIGHT_ON,        /* object=灯模型：灯打开 */
    MSG_DEV_LIGHT_OFF,       /* object=灯模型：灯关闭 */
    MSG_DEV_CCT_TEMP,        /* object=色温灯模型：色温变化 */
    MSG_DEV_CURTAIN_POS,     /* object=窗帘模型：开合度变化 */
    MSG_DEV_ALL_LIGHTS_OFF,  /* object=NULL：全屋断电广播（信号级广播示例）*/

    /* → g_ui_slot：生命周期 */
    MSG_DEV_ADD_MODEL,   /* object=模型（创建页面并绑定）*/
    MSG_DEV_DEL_MODEL,   /* object=模型（销毁绑定页面）*/
    MSG_DEV_MOVE_MODEL,  /* object=模型, arg0=new_pos */
    MSG_DEV_REFRESH_SYS, /* object=SYSTEM 模型 */
} box86_msg_type_t;

extern lv_slot_t g_ui_slot;    /* DEV → UI；UI 线程 50ms 定时器消费 */
extern lv_slot_t g_dev_slot;   /* UI → DEV；DEV 线程 wait+process 消费 */

8屏保功能

8.1 设计概述

屏保状态机由 screensaver.c 管理，两个独立 Page（"Screensaver"、"BlankScreen"）承载 UI；利用 lv_display_get_inactive_time() 跟踪无操作时长，由 1s LVGL 定时器轮询驱动。配置读取走 SYSTEM 模型快照。

8.2 状态机

┌────────┐ 无操作≥timeout(屏保开) ┌──────────┐ 屏保≥duration ┌────────┐ │ NORMAL │ ───────────────────────►│SCREENSAVER│ ─────────────► │ BLANK │ │ │ │ │ │ │ │ │ ◄────── 触摸退出 ────── │ │ │ │ │ │ └──────────┘ │ │ │ │ 无操作≥timeout(屏保关) │ │ │ │ ────────────────────────────────────────────────────►│ │ │ │ │ │ │ │ ◄──────── 触摸/wake 唤醒（wake_action=1 回首页） ──── │ │ │ │ ◄──────── 触摸/wake 唤醒（wake_action=0 回屏保） ──── │ │ └────────┘ └────────┘

8.3 关键逻辑

  1. NORMAL → SCREENSAVER/BLANK：1s 定时器检查 inactive_ms ≥ screensaver_timeout * 1000；屏保开启则打开 "Screensaver" 页，否则直接打开 "BlankScreen"。
  2. SCREENSAVER → BLANK：屏保页维持 screensaver_duration 秒后进入息屏。
  3. 唤醒（screensaver_wake，触摸或 Shell `wake`）：
    • BLANK：先 page_manager_back()；wake_action=1 继续 back_to_home() + home_page_reset_to_first() 回首页并置 NORMAL；wake_action=0 回屏保页重新计时（SCREENSAVER）
    • SCREENSAVER：page_manager_back() 返回原页面，置 NORMAL
  4. 唤醒后 lv_display_trigger_activity() 重置空闲计时。

9线程架构与业务交互

9.1 线程模型

线程职责槽角色
LVGL 线程（主线程）渲染、输入、页面导航、屏保状态机（1s 定时器）、UI 槽消费（50ms 定时器）、快照读取g_ui_slot 唯一消费者；g_dev_slot 发送方
DEV 线程（业务）g_dev_slot 消费（wait+process）、Shell 解析、模型增删改（唯一写方）、按信号经 g_ui_slot 通知 UIg_dev_slot 唯一消费者；g_ui_slot 发送方

两线程不直接共享数据结构：UI 消息经 g_dev_slot 发往 DEV；DEV 的模型变更按信号经 g_ui_slot 通知 UI。所有共享结构（槽队列/订阅链表、模型仓库）由互斥锁保护；槽的消息队列与订阅表均为动态链表节点，完全无上限。

9.2 消息流向

用户触摸 UI │ ▼ LVGL 线程（控件回调） │ lv_slot_send(g_dev_slot, {MSG_UI_SET_PROP, object=模型, field, value}) ▼ DEV 线程（slot_wait + process） │ 修改数据模型（唯一写方）→ Shell 输出 [UI] set ... │ 按状态发信号：lv_slot_send(g_ui_slot, {MSG_DEV_LIGHT_ON, object=同一模型}) ▼ LVGL 线程（50ms 定时器 → slot_process(g_ui_slot)） │ 按 signal + object 投递给订阅页面 ▼ 页面回调 on_msg：object 已由槽匹配 → model_store 快照读取 → 刷新控件

9.3 设备/模型生命周期管理

添加模型：

1DEV：Shell add → 创建模型入 store（唯一 ID）
▶
2send(g_ui_slot, ADD_MODEL, object=模型)
▶
3Home（订阅 ADD_MODEL，object=NULL）命中：创建 tile + 设备页
▶
4设备页 page_bind_slot(各信号, object=模型) + 记录绑定对象

删除模型（关键：防止 UI 访问已释放的模型）：

1DEV：send(g_ui_slot, DEL_MODEL, object=模型)（不释放）
▶
2Home on_msg（DEL_MODEL, object=NULL）：page_destroy(设备页) → 自动退订
▶
3Home 命中：移除 tile → 重排坐标 → 发送 ACK
▶
4DEV 收到 DEL_ACK(object=模型) → model_store_del 释放

删除时必须先销毁 UI 页面，再释放数据模型，顺序不可颠倒。

9.4 UI 与模型的解耦与绑定原则

  • UI 页面按信号 + 对象订阅（page_bind_slot(page, slot, signal, object)），object 由槽匹配，on_msg 无需再做实例过滤
  • UI 读取数据时通过仓库快照接口（锁内拷贝）；DEV 线程是模型唯一写方与所有者
  • LVGL 线程是 UI 控件唯一所有者；page_destroy 自动退订槽，杜绝悬垂订阅
  • 多实例场景：3 个灯 → 3 个页面各自以模型为 object 绑定；1 个灯 → tile 页 + 信息浮层共绑同一 object，同一条信号同时命中
  • 信号级广播：如"全屋断电"发送 MSG_DEV_ALL_LIGHTS_OFF(object=NULL)，订阅该信号的灯页因 NULL 双向通配命中，未订阅该信号的窗帘页不受影响；回调如需区分广播可判断 msg->object == NULL

11字体引擎评估：FreeType vs TinyTTF

11.1 评估背景

LVGL 9.x 内置支持两种矢量字体引擎：

  • TinyTTF：基于 stb_truetype，单头文件，零外部依赖，随 LVGL 源码一同编译
  • FreeType：独立字体渲染库，需要系统预装或交叉编译，功能完整，工业级

box86 项目最终选用 FreeType。本章记录两者的详细评估，供后续项目选型参考。

11.2 代码量与集成复杂度

指标TinyTTF（stb_truetype）FreeType
集成方式单头文件，随 LVGL 源码编译外部库，需安装或交叉编译
LVGL 集成代码量lv_tiny_ttf.c 约 717 行lv_freetype.c 等共约 1700 行
引擎自身代码量stb_truetype_htcw.h 约 5600 行（含注释）FreeType 库本身约 20 万行（含所有模块）
依赖管理无外部依赖需要 libfreetype（共享库约 795KB）
CMake 配置仅开启 LV_USE_TINY_TTF，无额外步骤需配置头文件路径、链接 libfreetype
移植到新平台极简，几乎零配置需确认目标平台预装或交叉编译 freetype

结论：TinyTTF 集成更简单，适合快速原型；FreeType 集成复杂度较高，但可通过工程内置头文件（third_party/freetype2/）降低配置门槛。

11.3 字体格式支持

格式TinyTTF（stb_truetype）FreeType
TTF（TrueType，glyf 轮廓）完整支持完整支持
OTF/CFF（PostScript 轮廓）部分支持：能解析 CFF 数据结构，但光栅化路径存在断言缺陷（STBTT_assert(0)），实际渲染汉字时输出方块完整支持
TTC（字体集合）部分：索引获取有 @TODO 注释完整支持
CJK 高字节映射（cmap format 2）明确标注 @TODO: high-byte mapping for japanese/chinese/korean，汉字可能无法正确映射完整支持
可变字体（Variable Fonts）不支持支持（FreeType 2.10+）
字体 Hinting基础支持（autohint）完整支持（TrueType hinting + autohint）
SVG/COLR 彩色字体不支持支持（需开启对应模块）

关键发现：box86 原使用思源宋体 OTF 格式（SourceHanSerifCN-Regular.otf），属于 CFF/OTF 格式。stb_truetype 虽然有 CFF 解析代码，但光栅化路径对 CJK 汉字存在 STBTT_assert(0) 断言，实际测试中所有汉字均渲染为方块。现已更换为同款字体的 TTF 格式（SourceHanSerifCN-Regular.ttf），TinyTTF 理论上可以处理，但仍建议使用 FreeType 以规避 CJK cmap 兼容性风险。

11.4 内存消耗

代码段（Flash/ROM）

TinyTTFFreeType
引擎代码段（估算）~50–80 KB（编译进可执行文件）共享库约 795 KB；若静态链接约 300–500 KB（可通过模块裁剪）

TinyTTF 作为单头文件编译进应用，没有动态库开销；FreeType 作为共享库仅在内存中加载一份，多进程可共享。

TinyTTFFreeType

字形缓存依赖 LVGL 的 glyph cache（LRU）内置缓存（Cache Manager），可精细配置
每字形渲染临时内存约 1–4 KB/字形约 2–8 KB/字形（轮廓处理更复杂）

栈内存

TinyTTFFreeType
LVGL 渲染线程栈需求约 8–16 KB 即可（官方建议 16 KB）官方要求最低 32 KB，建议 64 KB

box86 工程中 LV_DRAW_THREAD_STACK_SIZE 已从默认值改为 (64 * 1024) 以满足 FreeType 需求。

嵌入式 Linux 建议：RAM 紧张（<32 MB）时优先 TinyTTF；RAM 充裕时 FreeType 因惰性加载反而更节省常驻内存。

11.5 汉字渲染速度（实测数据）

测试环境：x86-64 Linux，-O2 编译，字体 SourceHanSerifCN-Regular.ttf（12.4 MB），字号 20px。测试工具：tools/font_bench.c，直接调用引擎 C API，绕过 LVGL 层，每项重复 3 次取均值。

渲染耗时对比

测试项stb_truetype (TinyTTF)FreeType倍率
字体初始化（含文件读取）~18,700 us~3,300 usFreeType 快 5.7×
首次渲染单个汉字（U+4E2D '中'）~17 us~960 usstb 快 57×
重复渲染同字均值（1000次）~1.7 us~4.2 usstb 快 2.5×
渲染 100 个不同汉字（合计）~730 us（均值 ~7.3 us/字）~1,580 us（均值 ~15.8 us/字）stb 快 2.2×

说明：FreeType 首次渲染耗时远高于后续渲染，原因是首次调用触发字体内部模块初始化（cmap 解析、hinting 引擎初始化等），属于一次性开销。第一次运行进程时因系统页面缓存未预热，实测可达 800–1000 us；文件已缓存后约 900 us，偏差约 10%。

内存占用对比

指标stb_truetypeFreeType
字体文件加载方式全量读入堆内存（12.4 MB）惰性映射，仅解析表头
字体加载后堆增量字体文件大小（~12,400 KB）+ 少量结构体~7 KB

关键差异：stb_truetype 需要在初始化时把整个字体文件读入堆（思源宋体约 12 MB），而 FreeType 惰性加载，初始堆开销仅约 7 KB，但每个字形缓存的 bitmap 数据积累后常驻内存会高于 stb。

对嵌入式 Linux（如 RK3506）的推断

  • 首次渲染：ARM Cortex-A7 @ 1 GHz 约为 x86 的 3–5 倍耗时，FreeType 首次渲染单字预计约 3–5 ms，stb 约 50–100 us
  • 重复渲染：两者均在 us 量级，结合 LVGL glyph cache（默认缓存 256 字形），UI 刷新时绝大多数字符命中缓存，引擎速度差异对帧率影响极小
  • 内存：嵌入式设备 RAM 通常在 64–256 MB，FreeType 的 119 KB 常驻开销可接受；stb 需要常驻 12 MB 字体 buffer，对内存敏感场景有压力
  • RK3506 等平台的 UI 渲染瓶颈通常是 RGA/GPU blending，字体光栅化并非瓶颈

11.7 选型建议

场景推荐引擎原因

MCU（无 OS，RAM < 8 MB）TinyTTFFreeType 体积过大，移植复杂
嵌入式 Linux（RAM ≥ 32 MB）FreeType系统通常预装，共享库节省整体内存，质量更高

box86 选型结论：使用 FreeType，原因如下：

  1. 字体文件为 TTF 格式（思源宋体），TinyTTF 理论可用，但 stb_truetype 对 CJK cmap format 2 有已知 @TODO 缺陷，存在不兼容风险
  2. 目标平台 RK3506 运行 Linux，RAM 充足，系统可预装 libfreetype
  3. 中文界面对渲染质量有要求，FreeType 的 hinting 在小字号下效果更好
